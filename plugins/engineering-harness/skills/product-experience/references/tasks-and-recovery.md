# Tasks and recovery

Trace arrival → decision/action → visible result → next useful action. For each
material branch, ask what the user must know beforehand, what remains available,
what work is preserved, and how to leave or recover. A button press is not success.

Select states from actual forces: missing/filtered data, partial loading, stale
inputs, delayed effects, denied permissions, validation, interruption, offline
operation, conflicting updates, or irreversible actions. Distinguish unknown from
empty and pending from failed. Preserve manual input and explain whether a result
is an estimate, proposal, saved fact, or obsolete output. Do not enumerate every
possible state for an unrelated local edit.

For IA, map user concepts and existing destinations before adding another entry.
Distinguish immediate tasks, current status, history, configuration, and rare
operator tools. Different audiences may need disclosure rather than additional
top-level navigation. Removing or combining destinations can change an accepted
contract just as adding one can; follow the existing scope gate.

Assess cognitive effort in context: recognition versus recall, unclear choices,
interruption/re-entry, and visible completion. Density can help experts; active
physical use may need different priority and targets. Heuristics generate questions,
not universal card counts, CTA limits, or measured usability scores.

Record only consequential decisions in the existing task record. If the contract
cannot support the requested outcome, return the existing
[scope approval handback](../../../references/scope-approval.md) and continue
independent authorized work. Delegate persistence, account fencing, and resource
architecture to their accepted owners rather than specifying a new UI-owned system.
