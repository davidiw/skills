# Repository design authority

Find accepted product/design documents, tokens, components, assets, and representative
renderings before describing a language. Existing DESIGN.md may own architecture
and product contracts; preserve it and use a linked section or subordinate design
document. A generic skill supplies judgment, not project-specific taste.

- **Document:** describe established reality with source/rendering provenance.
  Separate accepted intent, observed implementation, drift and unknowns. A polished
  screen does not automatically overrule an explicit accepted contract.
- **Merge:** preserve unique accepted local rules and one authority. Surface
  contradictions rather than silently selecting old screenshots or newer code.
- **Propose:** when direction is missing or materially changing, brand-and-language
  owns the identity/visual-intent proposal; product-experience owns product/IA changes.
  Record explicit approval and limits through the existing scope gate before
  treating a proposal as accepted or applying it to production.

Use only applicable dimensions: audience/job; atmosphere and visual intent;
semantic color roles; type roles; density/layout; spacing/elevation; component
treatment; responsive and interaction principles; vocabulary/voice; concrete
examples; provenance and open questions. Prefer a compact document linked to real
tokens/components over copied values or universal aesthetic budgets.

Documentation is not permission to restyle the product. Missing documents do not
authorize a new identity; inconsistent code does not authorize design-system
replacement. Preserve each surface's posture within the accepted identity: an
active tool, a reflective review and a marketing page need not look equally bold.
Do not copy another product's palette, logo, or trade dress into generic guidance.
