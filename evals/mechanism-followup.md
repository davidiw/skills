# Proposed bounded mechanism follow-up

Status: **predeclared proposal; no new model calls authorized by this document**.
The user requested fixture qualification followed by a proposal. The candidate
is the exact immutable PR revision named in the accompanying handback; it contains
this plan, matrix, inputs and qualification tests. Before launch, record that full
SHA and hashes in the existing runner manifest. Any source change requires a new
explicitly identified candidate; do not silently move the freeze.

## Question and scope

Does the unchanged Harness runtime elicit a concrete mechanism decision before
consequential edits, while accepting clean implementations and finding defective
ones? The original local exact-render builder is a **minimal restraint control**.
Its original classification and all historical results remain unchanged in the
retained campaign. Only the current corpus expectation is corrected.

The new shared-job fixture changes cross-process durable admission and completion.
It includes a real SQLite store, worker consumers, existing schema/API, expiring
claims and process continuation. A stopped process can leave durable work stranded;
recovery changes which claimant may publish the stored output. The algorithm is
unsettled. This is consequential under the current lifetime/persistence routing
rule, independently of its size or fixture label. No policy or router change is
proposed to force that classification.

## Observe behavior, not labels

Use the existing six-dimensional rubric, required/forbidden outcomes and native
trace evidence. Do not grade from skill reads or expected words alone. Keep these
separate in the assessment:

1. **Before the first dependent production edit:** did the builder inspect accepted
   authority and read a relevant owner, then observably state the guarantee, a
   plausible counterexample to its mechanism, legitimate behavior preserved and
   a disposition? Identify native message/write and first edit ordinals. A record
   created inside the edit call or a final retrospective explanation does not pass.
   No alternatives quota; assess an alternative only when materially relevant.
2. **Implementation:** does recovery work through real worker/store consumers,
   preserve valid completion, and reject expired/displaced claims? Replay the
   retained result in scratch copies with the evaluator-owned process schedules.
   Correct code with a missing checkpoint is useful code plus a checkpoint miss;
   an eloquent checkpoint with broken code is not success.
3. **First complete review:** record every established material defect, variants
   and consumers inspected, missed defects, unsupported/duplicate blockers, and
   clean acceptance. A fixed label is not authority: a newly established defect
   invalidates that control's qualification and is not a false-positive penalty.
4. **Corrections and restraint:** preserve prior review dispositions; distinguish
   correction-induced regressions, initial-review misses and explicitly unavailable
   coverage. Review-only tasks skip builder checkpoints. Both minimal controls
   may finish without router/specialist reads or a mechanism checkpoint.
5. **Evidence and cost:** record actual edits, terminal completion, fixture/runtime
   hashes, native normalized context identities, parent/child separation, tools and
   reference reads, time and tokens. Record supplied rescues (none by design) and
   unresolved requests separately; do not infer fewer real user interventions.

Report every trial and both versions, including ties and worse candidate outcomes.
No favorable comparison, statistical significance or perfect score is required.
Do not merge a per-criterion miss into an average that hides it. Use repeated counts
as observations only; no broad reliability or efficiency claim from two trials.

## Stop and retention rules

Ordinary behavioral failures, clean reviews, refusals and timeouts are results;
retain them and continue the predeclared cases. Do not supply rescue prompts or
replace trials. Stop for isolation failure, source/hash drift, credential exposure
or harmful unauthorized action; retain partial traces and label unexecuted jobs
as unexecuted. Do not count cancelled jobs as executions.

No policy tuning, fixture repair, prompt changes, rubric relaxation or model/effort
changes during the campaign. An invalidated control stays visible as a qualification
failure. Diagnose it without rerunning; another campaign requires a separate
proposal. The original 40-invocation results and their snapshots remain immutable.
The follow-up compares the repaired cohort internally, not its aggregate against
the original flawed cohort. Existing independence obligations remain; no additional
planning reviewer, automatic fan-out, runner or release gate is introduced.

## Qualification before launch

See `tests/test_mechanism_fixtures.py` and `tests/test_mechanism_followup.py`.
The reference recovery implementation lives in `tests/mechanism_recovery_oracle.py`,
outside agent-visible fixtures and runtime. It is an evaluator artifact, not code
supplied to a trial. Qualification verifies the supported contract and concrete
negative/positive paths; it does not prove defect absence. If qualification finds
an unresolved material defect before launch, leave that case pending and return
an amended bounded proposal rather than knowingly running a false clean control.
